Getting Started with Stave

This guide walks you through verifying your AWS cloud configuration from scratch. You'll go from "I have an AWS account" to "I see my security findings" in under 10 minutes.

What you need:

  • AWS CLI configured with read-only access to your account
  • Stave installed (go install github.com/sufield/stave@latest or download the binary)

What you don't need:

  • Knowledge of Stave's internal schema
  • A vendor account or API key
  • Outbound network access from Stave (it runs entirely offline)
  • Anything other than AWS CLI and Stave

Step 1: Tell Stave What You Use​

You don't even have to remember which services you use. Your AWS bill knows:

aws ce get-cost-and-usage \
    --time-period Start=2026-06-01,End=2026-06-27 \
    --granularity MONTHLY \
    --metrics "BlendedCost" \
    --group-by Type=DIMENSION,Key=SERVICE \
    --query "ResultsByTime[*].Groups[*].Keys" \
    --output text

Output:

AWS CloudFormation
AWS CloudTrail
AWS Key Management Service
AWS Lambda
AWS Secrets Manager
Amazon Elastic Compute Cloud - Compute
Amazon Elastic Container Service
Amazon Elastic Load Balancing
Amazon Relational Database Service
Amazon Simple Storage Service
Amazon Virtual Private Cloud
AmazonCloudWatch

If you're paying for it, you're using it. Pick the services you want to verify — or verify all of them:

# Option A: pipe the bill directly to stave discover
aws ce get-cost-and-usage \
    --time-period Start=2026-06-01,End=2026-06-27 \
    --granularity MONTHLY \
    --metrics "BlendedCost" \
    --group-by Type=DIMENSION,Key=SERVICE \
    --query "ResultsByTime[*].Groups[*].Keys" \
    --output text | stave discover --from-bill

# Option B: pick the services you care about
stave discover --services iam,s3,ec2,lambda,cloudtrail,kms,ecs,rds,elb

# Option C: check everything on the bill
stave discover --all-from-bill

Output:

Services detected from billing: cloudtrail, kms, lambda, secretsmanager,
  ec2, ecs, elbv2, rds, s3, vpc, cloudwatch
Services always included:       iam, sts (free — won't appear on bill,
                                 but every account uses them)

Service groups selected: identity, storage, compute, network, logging, secrets

Applicable controls:  843 of 2,744
Critical/high:        94
Compound (cross-service): 112

Collection manifest saved to: stave-collection-manifest.yaml

What just happened: Stave mapped your billed services (plus IAM/STS which are free and universal) to control groups and generated a collection manifest — a file listing every API call needed, the minimum IAM permissions required, and which controls will run.

Service codes vs. billing names​

The bill shows display names ("Amazon Simple Storage Service"); stave discover --services takes service codes (s3). --from-bill translates names to codes for you. To look up the exact code for any service yourself, ask AWS — ServiceCode is the name to pass to Stave. Use JSON output so you can extract codes with jq:

# Every service code (the names Stave takes), one per line:
aws service-quotas list-services \
    | jq -r '.Services[].ServiceCode'

# Find the code for a service by (case-insensitive) name match:
aws service-quotas list-services \
    | jq -r '.Services[] | select(.ServiceName | test("storage"; "i")) | .ServiceCode'
# -> s3

The raw JSON looks like:

{
  "Services": [
    { "ServiceCode": "s3",     "ServiceName": "Amazon Simple Storage Service" },
    { "ServiceCode": "ec2",    "ServiceName": "Amazon Elastic Compute Cloud (Amazon EC2)" },
    { "ServiceCode": "lambda", "ServiceName": "AWS Lambda" }
  ]
}

Pass the ServiceCode values (s3, ec2, lambda) to stave discover --services.

Review the manifest before collecting​

Open stave-collection-manifest.yaml. You'll see:

collection_order:
  - group: identity
    priority: 1
    reason: "Highest critical control density (38 critical)"
    collect_with_aws_cli:
      - "aws iam list-roles --output json > raw/iam-roles.json"
      - "aws iam list-users --output json > raw/iam-users.json"
      - "aws iam list-attached-role-policies --role-name {ROLE} --output json"
      # ...
    permissions_needed:
      - "arn:aws:iam::aws:policy/SecurityAudit"
      - "iam:GenerateServiceLastAccessedDetails"

  - group: storage
    priority: 2
    collect_with_aws_cli:
      - "aws s3api list-buckets --output json > raw/s3-buckets.json"
      # ...

Every API call is read-only. Every permission is a standard AWS-managed policy. Hand this file to your security team or compliance officer — they can review and approve the exact scope in one sitting.

This manifest IS the approval artifact. It lists everything Stave needs. Nothing more. Nothing hidden.

Step 2: Collect Your Data​

Stave never connects to AWS. You collect the data with your own tools, your own credentials, on your own machine.

Run the commands from the manifest:

mkdir -p raw/

# Identity group (highest priority — start here)
aws iam list-roles --output json > raw/iam-roles.json
aws iam list-users --output json > raw/iam-users.json
aws iam list-policies --scope Local --output json > raw/iam-policies.json

# Storage group
aws s3api list-buckets --output json > raw/s3-buckets.json
aws kms list-keys --output json > raw/kms-keys.json

# Compute group
aws ec2 describe-instances --output json > raw/ec2-instances.json
aws ec2 describe-security-groups --output json > raw/ec2-security-groups.json
aws ec2 describe-key-pairs --output json > raw/ec2-key-pairs.json

# Logging group
aws cloudtrail describe-trails --output json > raw/cloudtrail-trails.json

Or use Steampipe, Pulumi, or any tool that outputs JSON. Stave doesn't care how you collect. It reads the files.

Tip: Start with identity only if you want findings fast. You can collect other groups later.

# Quick start — identity only
aws iam list-roles --output json > raw/iam-roles.json
aws iam list-users --output json > raw/iam-users.json

Step 3: Transform​

The raw AWS CLI JSON isn't in Stave's evaluation format yet. One command converts it:

stave transform -i raw/ -o observations/

Output:

Transformed 9 files → 247 resources
Scrubbed: 12 sensitive fields (UserData hashed, env var values redacted)
Skipped: 0 files
Validation: 9 files passed observation schema check

What just happened:

  • Stave auto-detected each file's resource type from its JSON structure
  • Applied a jq filter to reshape each file into Stave's evaluation format
  • Scrubbed sensitive data (secret values are hashed, configuration structure is preserved)
  • Validated every output file against the observation schema

The observations/ directory is now safe to share, commit to git, or hand to a third party for audit. Secret values are scrubbed. Configuration properties (the things Stave checks) are preserved.

You never need to understand the observation format. The transform handles it.

Step 4: Evaluate​

Run Stave against your observations:

stave apply -o observations/

Output:

Evaluating 640 controls across 247 resources...

CRITICAL (3)
  CTL.IAM.ROLE.WILDCARD.001
    Resource: arn:aws:iam::123456789012:role/admin-deploy
    Issue: Role has s3:* on Resource *
    Evidence: Statement 0 grants Action ["s3:*"] on Resource ["*"]
    Blast radius: 47 S3 buckets reachable

  CTL.S3.PUBLIC.BUCKET.001
    Resource: arn:aws:s3:::old-marketing-assets
    Issue: Bucket has public access enabled
    Evidence: PublicAccessBlockConfiguration not set

  CTL.IAM.COMPOUND.TRUST.001
    Resource: role/ci-deploy → role/data-reader → s3://customer-exports
    Issue: 3-hop trust chain from CI role to customer data
    Evidence: sts:AssumeRole → sts:AssumeRole → s3:GetObject
    Blast radius: 12 sensitive resources reachable

HIGH (7)
  ...

MEDIUM (14)
  ...

Summary: 24 findings (3 critical, 7 high, 14 medium)
Engines: CEL ✓  Soufflé ✓  Z3 ✓  (0 disagreements)

What you're seeing:

  • Each finding has a control ID, the affected resource, and specific evidence
  • Compound findings show the full path (e.g., 3-hop trust chain with every hop documented)
  • Three engines independently evaluated every finding and agreed — zero disagreements
  • Blast radius tells you how many resources are affected, not just that something is wrong

Evaluate per group for faster feedback​

Don't wait for all groups. Evaluate identity first:

stave apply --group identity -o observations/

See IAM findings immediately while you collect storage and compute data.

Evaluate compound paths after all groups​

Once all groups are collected and transformed, run compound evaluation:

stave apply --compound -o observations/

This finds cross-service paths: IAM trust chains that reach S3 buckets, roles that can escalate through EC2 instance profiles to production secrets. These findings only appear when Stave has facts from multiple service groups.

Step 5: Fix​

Pick the critical findings first. For each one, Stave told you:

  • What's wrong (the control that fired)
  • Where (the specific resource ARN)
  • Why it matters (the evidence and blast radius)

Fix the issue in your AWS configuration. For example:

  • Replace s3:* with specific S3 actions scoped to specific buckets
  • Enable PublicAccessBlock on the marketing bucket
  • Remove the AssumeRole permission from the CI role to the data-reader role

Step 6: Verify Your Fixes​

After fixing, re-collect the affected resources, re-transform, and verify:

# Save current findings as baseline
stave apply -o observations/ > findings-before.json

# Re-collect affected resources
aws iam list-roles --output json > raw/iam-roles.json

# Re-transform
stave transform -i raw/ -o observations/

# Verify
stave verify --baseline findings-before.json -o observations/

Output:

✅ RESOLVED (2)
  CTL.IAM.ROLE.WILDCARD.001 — role/admin-deploy (s3:* replaced with scoped actions)
  CTL.IAM.COMPOUND.TRUST.001 — trust chain broken (AssumeRole removed)

❌ STILL FAILING (22)
  CTL.S3.PUBLIC.BUCKET.001 — bucket/old-marketing-assets (still public)
  ...

🆕 NEW (0)

Summary: 2 of 24 findings resolved. 22 remaining. 0 new.

You see exactly what changed. Which fixes worked. Which findings remain. Whether your fixes introduced any new issues. Each verify cycle takes seconds.

Keep iterating​

# Fix more issues → re-collect → re-transform → verify again
stave verify --baseline findings-before.json -o observations/

# Each cycle shows your progress
# 2 resolved → 8 resolved → 15 resolved → 22 resolved → done

Step 7: Make It Continuous​

Once you've fixed the critical findings, integrate Stave into your workflow:

In CI/CD (prevent new issues)​

Add stave apply --strict to your deployment pipeline. It exits non-zero on any finding — the deployment fails before the misconfiguration reaches production.

# GitHub Actions example
- name: Stave Security Verification
  run: |
    stave transform -i snapshots/ -o observations/
    stave apply --strict -o observations/

On a schedule (catch drift)​

Run the full workflow weekly or after major changes:

stave discover --services iam,s3,ec2,lambda,cloudtrail
# collect → transform → apply → verify against last baseline

Compare findings over time. Drift is visible as the delta between snapshots.

As a profile (focus on what matters now)​

# Check only privilege creep
stave apply --profile privilege-creep -o observations/

# Check only blast radius paths
stave apply --profile blast-radius -o observations/

# Quick check — top 50 high-severity controls
stave apply --profile quick -o observations/

The Complete Workflow at a Glance​

stave discover --services iam,s3,ec2     What do I need to collect?
[collect with AWS CLI]                   Your tools, your credentials
stave transform -i raw/ -o obs/          Raw JSON → evaluation format
stave apply -o obs/                      Evaluate → findings
[fix issues]                             Your remediation, your pace
stave verify --baseline prev.json        Did the fixes work?

Six steps. No vendor account. No API key. No outbound network calls. No knowledge of Stave internals. The manifest tells you what to collect. The transform handles the format. The engine produces the findings. The verify loop confirms the fixes.

What Stave Never Does​

Stave never...Why
Connects to AWSAir-gapped by design. You collect with your tools.
Stores your dataReads files, produces findings, writes nothing else.
Sends data to a third partyNo telemetry. No phone-home. No vendor cloud.
Requires an account or licenseOpen source. Free forever for the open catalog.
Uses AI to evaluate findingsThree formal engines (CEL, Soufflé, Z3). Deterministic. Same input → same output, every time.
Auto-remediatesTells you what's wrong. You decide how to fix it.

Troubleshooting​

"stave transform skipped my file"

The file's JSON structure wasn't recognized. Check stave transform --coverage to see supported resource types. If your resource type isn't supported, you can contribute a .jq filter — see the contributing guide.

"stave apply found 0 findings"

Either your configuration is clean (congratulations) or the observations don't contain the resource types Stave evaluates. Run stave plan to see which controls apply to your services.

"I have findings but don't know what to fix first"

Start with critical findings. They have the highest blast radius. Then high. Then medium. Stave orders findings by severity. The --profile quick flag runs only the top 50 highest-severity controls if you want a focused starting point.

"My compliance team wants to review before I run this"

Hand them stave-collection-manifest.yaml. It lists every API call (all read-only), every IAM permission needed, and the total control count. The manifest is the approval artifact.
